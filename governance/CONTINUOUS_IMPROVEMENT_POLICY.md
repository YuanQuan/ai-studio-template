# 持续改进策略

策略 ID：CI-001。规则文本版本：1。适用范围：已采用本策略的 Studio / Game Repository。集成与工具状态以 `governance/IMPLEMENTATION_STATUS.md` 为准。

本策略固化用户已经确认的工作方法：主动发现协作问题，在限定范围内改进，并把依据和结果写入仓库。它不授予工具权限，不覆盖应用安全检查，不构成 Git、外部发布或生产环境操作授权。

## 1. 授权边界

### A：低风险维护
可在当前用户授权的目录内修复明确的文档矛盾、断开的索引、重复描述、已有要求的校验缺失和状态展示错误。必须保留原有要求、事实、审批、质量标准及可追溯信息。记录修改依据、范围和实际验证，不必为同一既定要求重复询问用户。

### B：内部协作改进
兼容的任务拆分、交接顺序、责任澄清、重复交付精简、上下文加载方式和测试检查项改进，由 Master 组织受影响角色评审。先在当前项目验证，确认没有降低质量、破坏契约或增加未授权成本后应用。保留提案、评审、验证和回退依据。只有具备真实评审记录才能写“评审通过”；同一会话的自检不能冒充独立 Agent 审查。

### C：仍须用户明确决定
产品目标、玩法、数值、商业化、付费、重大架构或技术栈、破坏性 API / 存档变更、额外预算、降低质量门槛、移除用户审批，以及新增敏感数据或生产环境访问，不能依据本策略自行决定。

本策略及其权限分类、受保护边界、Git 授权和用户批准规则自身的修改，仍须用户明确批准。不得先修改授权规则，再依据新规则扩大权限。

## 2. 受保护原则

- 不得为取得 PASS 删除必要用例、修改产品期望、放宽阈值或掩盖未测试范围。
- 不改写已批准历史 Artifact、批准记录、旧测试结果及真实提交版本。
- 正式游戏产物的逐环节用户审批保持不变；内部治理改进不等于游戏功能获得批准。
- 工具拒绝、设备离线或缺少权限时记录阻塞，不换工具或路径绕过同一安全拒绝。
- 用户的目录限制优先于默认同步规则。仅修改模板时不得写入任何具体游戏仓库，也不得通过脚本、链接或复制间接修改。
- 文件级改进不授权 add / commit / push / fetch 或其他 Git 动作；上线测试通过不授权实际发布。

## 3. 触发点与职责

任务退回、QA 失败、交接阻塞、重复返工、职责争议、预算超限和任务结束时进行简短检查。不要求每个普通 Bug 都成为永久规则，也不要求每个任务生成长篇复盘。

专业 Owner 提交事实与证据；Producer 归并重复问题、维护记录与展示；Master 判断授权和范围、组织评审；Tech Lead 检查兼容性与实现复杂度；QA 检查改进效果与质量回归。没有可用独立执行器时如实标明，不伪造多 Agent 已运行。

只在实际运行中的会话或已部署执行器内触发；不能声称无执行器时仍在后台调优。

## 4. 最小闭环

问题与证据 -> 原因判断 -> 最小修改 -> 评审 -> 当前范围验证 -> 保留或回退 -> 通用方法推广。

项目记录放入 `project/improvements/<ID>.md`；模板组织维护记录放入 `governance/capability_changes/<ID>.md`。每条至少包含：ID、来源、问题、证据路径、风险分类、授权依据、Owner / Reviewer、修改范围、预期收益、实际验证、回退办法、适用规则版本和同步状态。

记录状态可以使用 PROPOSED / REVIEWED / TRIAL / VERIFIED / APPLIED / REVERTED / BLOCKED，但这些是治理记录状态，不是旧 Task 的 status 枚举。

用户亲自批准记为 USER_EXPLICIT；在 CI-001 既有授权范围内处理记为 STANDING_POLICY；专业审查结论记为 PROFESSIONAL_REVIEW。不得把后两者伪装成新的 USER_APPROVED。

现有 JSON Schema 尚未扩展时，内部治理记录使用上述 Markdown 结构；正式游戏任务和审批继续符合现有 Schema，不添加未知字段，不给 user_approval 填写虚假批准。

## 5. 验证与投入

确定的规则矛盾可及时修正；经验性改进先小范围试验。验证应检查原问题、相关质量条件、兼容性与返工情况；没有费用或 token 数据时写未知，不编造节省比例。

采用最小改动；自动修复最多两轮，仍失败提交诊断并停止该条改进。大型工具工程、额外服务费用或影响项目排期的扩大工作，必须另立范围并取得必要批准。本策略不授权无限制自我优化。

## 6. 会话和规则版本

遵守 `rules/session_protocol.md`。运行中的任务固定其输入和规则依据；改变验收、职责、输入或输出要求时，在安全交接点通过差异计划迁移，不在中途静默切换。

关键节点立即落盘，不只依赖会话结束总结。多人或多会话同时工作时采用单写者与修改前复核；未实现原子锁时不得声称已具备并行写入保障。

## 7. 项目经验回流

只有经过验证、去除项目特定内容、通过影响评审、且属于 A / B 类的通用方法，才可在已授权的模板目录内回流。产品细节、资源、数值、业务代码和项目历史留在游戏仓库。

当前参与项目可在安全节点采用；其他游戏保持各自锁定版本。模板不可访问或不在本轮范围时记录 PENDING_TEMPLATE_SYNC，不宣称完成双同步。

遵守 `governance/REPOSITORY_SYNC_POLICY.md`；不伪造 `.studio-lock.json` 的 commit。本地应用、已经验证、已经提交和已经推送是四种不同事实。

## 8. 用户可见性

Producer 在 Dashboard 和恢复索引中简要显示已应用改进、证据、风险、同步与回退状态。内部改进默认汇总，不重复要求用户处理同一流程问题；涉及 C 类、真实阻塞或重要项目影响时再请用户决定。
