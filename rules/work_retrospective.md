# Producer 每轮工作流程复盘

## 触发与边界

每次工作推进到一个可说明的结果时，Producer 在本轮结束前完成一条简短复盘。这里的“一次工作”指同一授权下，从开始实际执行到产物提交、专业 Review、用户审批门禁、明确阻塞、取消或 DONE 的一个执行周期；不要求为每个命令、每次聊天或每个微小编辑单独建记录。跨会话继续时分别记录各执行周期，并关联相同 Task / Artifact 版本。

复盘是流程观察，不改变 Task 状态、Artifact 审批、专业结论或 QA 结论；不能因撰写复盘停下仍可继续的授权工作。先完成真实产物和必要门禁，再将复盘写入当前游戏 `project/WORK_RETROSPECTIVE_LOG.md`，在 `WORKFLOW_STATUS.md` 或 Dashboard 给出最近一条记录的索引。Producer 负责汇总与判断流程原因；专业 Owner 提供事实和证据，Master 决定跨角色建议的后续任务或变更路径。

## 每条记录的最小内容

1. 执行周期 ID、关联 Task / Artifact 及版本、Owner、实际结果、证据路径和当前门禁状态。
2. 可核对的开始/结束时间、时区与耗时；只有部分时间可知时分别列出已知节点，把总耗时写为“未知”。区分实际执行、依赖等待、用户审批等待、专业 Review、返工和工具故障。不得把跨日的总历时全部称为 Agent 制作时间。
3. 判断是否“慢”的依据：约定目标、同类历史、关键路径延误或明确阻塞。没有可比基线时写“尚无基线”，仍指出可观察的等待或返工；不能凭主观感受给角色归责。
4. 主要原因、证据与不确定性，区分直接观察和推断。没有明显瓶颈时写“本轮未发现可证实的慢因”。
5. 最多三条可执行建议，写明责任角色、预期减少的等待/返工环节、代价或风险、下一次复核节点；不能以“提高效率”代替具体动作。

记录应简短。重复问题可以引用既有记录，不复制长篇分析。重大或反复发生的改进才按 `governance/CONTINUOUS_IMPROVEMENT_POLICY.md` 进入 `project/improvements/<ID>.md`，由 Master 组织相应评审和试验；涉及产品、技术栈、成本、权限、质量底线或审批规则的建议走既有变更与用户决定，不由 Producer 单方生效。

## 复核

Producer 在下一次相似工作或相关门禁结束后，对已采纳建议记录“有效 / 无效 / 证据不足”及证据，必要时回退。旧任务不追补虚构时间；本规则生效后的新执行周期开始记录。复盘完成情况应在每轮最终汇报中简要可见，但复盘本身不是下游 Artifact Gate。
