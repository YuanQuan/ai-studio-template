# 视觉设计到正式资源的交接契约

本规则适用于场景、角色、建筑、道具、UI 和 VFX 中需要制作图片或运行画面的任务。它规定各角色如何继承已确认的视觉设计，并与 `rules/artifact_contract.md`、`rules/approval_protocol.md` 共同使用。具体游戏的画风、配色、角色形象和资产数值仍由该游戏已批准的 Art Artifact 与 `project/ART_GUIDE.md` 决定。

## 1. 设计基线与原创重绘

- Art Director 将用户批准或明确采纳的效果、概念和设计意图转成有版本号的视觉基线。正式生产前，`VISUAL_ANCHORS.md` 或等价 Art 文档逐项写明：轮廓/比例、视角/构图、材质/明暗/光感、色彩关系、身份元素、动作/状态、空间/遮挡、实际显示尺度，以及每项必须保持、可调整和需重新审批的范围。
- 效果图与概念图是设计依据，不自动成为可裁切、可描摹、可直接导入的生产图片。执行美术须依据锚点制作可编辑的原创母版，同时登记参考来源、许可、工具/字体权利和可识别相似风险。不能为追求一致性复制受保护表达，也不能以“重新绘制”为由自行更换已确认的造型、材质或视觉主次。
- 产品、镜头、动画方式或技术约束变化时，先列出原锚点中仍有效、失效和待决定的部分。只有实际受影响的锚点重新评审；不得把技术方案退回误当作所有视觉设计一并作废。

## 2. 出图与审查顺序

1. Master 的 Task Packet 引用已批准视觉基线，列出可检查的视觉验收和必需证据；Product 负责玩法/内容语义，Art 负责视觉解释。
2. 代表样张首次出图前，Art 与 Tech Lead 对同一版本的来源/版权、母版格式、尺寸/画布、层/支点、帧/骨骼、图集/合批、目标设备预算与输出范围分别签认文字预案。签认只覆盖所列批次和工具；全量资源开工前以及换源格式、工具、尺寸、动画或资源范围时，在下一张图生成或导出前复签。尚无实图的预签只能写估算，不能伪称实测。
3. 高影响或将批量扩展的资源先做可编辑代表样张。Art 将已确认基线、被退回版本（如有）与新原创稿按同画幅、同游戏视窗和实际显示尺度并排，对每个视觉锚点记录 `PASS`、`REVISE` 或 `NOT_TESTED`、证据路径与原因；未通过的样张不得扩成整批。低影响单件可在成品评审中直接完成同样对照。
4. 代表样张先由 Art 对实图给出视觉结论，再由 Tech Lead 按实际 alpha 范围、页数、贴图面积和投影像素复核生产方案；两者均通过且全量预案复签后才扩为整批。成品仍分别取得 Art 视觉结论与 Tech 对实际贴图、内存、打包、合批和兼容性的结论。哈希、alpha、帧数、脚点、构建或性能 `PASS` 均不替代视觉 `PASS`；视觉 `REVISE` 不得送用户作为可批准的正式资源。
5. 当生产者与 Art Director 是同一 Agent 时，须保留逐锚点的自审证据，Master 对实际图片独立复核；有独立美术审稿人时优先由其复核。Master 不能只凭自评或技术数据放行视觉稿。专业评审通过后仍由用户审批具体版本，Client 只能正式接入获批资源。
6. Client 在同源版本的独立/组合/主体入口核实际视窗、状态、翻转、光影、遮挡和资源 ID，记录源/导出/Prefab 的版本、UUID 或 hash，保留截图/录屏与性能记录；QA 以已批准视觉基线做固定环境的视觉验证，按功能、视觉和性能分别报告。依 `rules/qa_protocol.md`，`FUNCTIONAL` 默认固定 Web/测试环境，`RELEASE` 才要求声明平台真机；单元任务若另有目标机要求，须在获批开工包写明设备、环境和阈值。未导入、未运行或无相应设备证据时明确 `NOT_TESTED`，静态预览不充当运行证明。

## 3. 技术与视觉冲突

画布、贴图页数、压缩、复用、帧数、骨骼、合批或设备预算均不自动授权改变已确认的视觉设计。若目标无法同时满足，Art 说明具体视觉损失，Tech Lead 给出测量或可复验估算、备选尺寸/分页/实现方式和成本；Master 组织受影响角色评审并把需要用户取舍的变化提交用户。未经决定不得把画面静默简化成示意图，也不得隐瞒实际性能超限。

## 4. 各角色交接

| 角色 | 必须负责的界面 |
|---|---|
| Product | 标明视觉元素承载的产品身份和不可改变的语义；不自行指定艺术画法。 |
| Art / Art Director | 锁定视觉锚点、原创母版与允许变化；对样张、成品、UI/VFX 可见变化做逐项视觉评审。 |
| UI / VFX | 在 Art 基线内完成各自结构、交互或触发/时序/性能规格；视觉偏离先提方案交 Art 评审，不以复用或降级自行换风格。 |
| Tech Lead | 对真实资源与预算做独立技术评审；不能用技术 `PASS` 宣称视觉 `PASS`，预算冲突上报取舍。 |
| Client | 只接入批准的资产版本与源 ID；程序适配、裁切、色调或效果变化涉及锚点时回 Art 评审，留下运行证据。 |
| Server | 若服务端配置引用视觉资产，仅维护获批稳定 ID/版本和数据语义；不以服务端字段/占位资源决定美术外观。 |
| QA | 分别核功能、运行性能和视觉锚点；缺少基线、画面或设备证据时记 `NOT_TESTED/BLOCKED`，视觉偏差按现行缺陷等级与审批门禁处理。 |
| Producer | 追踪设计基线、执行源、视觉/技术 Review、用户审批与返工版本；视觉未通过或版本错用时锁下游。 |
| Master | 组织跨角色取舍、在送用户前独立看图核锚点，不以文件齐备或静态检查替代视觉判断。 |

## 5. 最小证据与版本

需视觉基线的 Task 至少引用：批准的 Art Direction/概念版本、`VISUAL_ANCHORS.md` 或等价锚点文档、可编辑源与导出清单、同尺度对照图/截图或逐项说明、Art 视觉 Review、Tech 资源 Review、用户审批记录。适用时还需动画/状态视频与运行证据。每项结论须对应真实文件路径和版本；失败样张、用户退回稿保留历史，修订版不得覆盖旧审批。新规则只约束新任务和当前任务在安全交接点之后的新版本，不追溯伪造旧版 `PASS`。
